## 12 feature first / layer firstを選ぶ理由

04:40–05:25（45秒）

**画面**

> feature first / layer firstを選ぶ理由
>
> 機能のまとまりを追うなら feature first
>
> 責務の境界を追うなら layer first
>
> 自分は、機能横断と責務の変化を意識した

**話す**

feature firstは機能ごと、layer firstは責務の層ごとに先にまとめる配置です。自分は、業務では機能をまたぐ処理や責務の変化が多いと考えて、layer firstを選びました。人にもAIにも、置き場所と境界を意識してほしかったからです。

一方で、一つの機能の変更が複数の層に広がると、追う場所は増えます。feature firstでも層は分けられますし、どちらを先に見たいかはプロジェクト次第だと思います。

だしゅまる：座ったまま、呼吸や小さな揺れを続けます。

出典：[本人の選定メモ](https://github.com/yakitama5/material_github_searcher/blob/57d9662dcdbfe1a93e6bb0b4706bfa778db8ba05/docs/technical-decisions.md#L53-L67)。機能横断・責務の変化を意識してlayer firstを選んだ理由は本人の記録です。両方とも層を設けられ、ここでは配置の優先順を比較しています。得られる見通しと変更時に追う場所の説明は、記録をもとにした発表用の整理です。

## 13 MVVMで、何を分けたい？

05:25–06:10（45秒）

**画面**

> MVVMで、何を分けたい？
>
> 画面の状態と操作を、表示から分ける
>
> 画面の判断を、Widgetとは別に確かめる
>
> 分けた先に、同じ責務を重ねない

実例として「アプリ状態はApplication Providerへ集約」を添えます。

**話す**

MVVMなら、表示する側と、画面の状態や操作を扱う側を分けます。画面の判断が複雑で、Widgetとは別にテストしたいなら、その分離には意味があります。ただ、クラスを増やすなら役割も決めたい。

自分の実装では、アプリ状態をApplication Providerに集約し、画面専用のViewModelは追加していません。新しく置くなら、何をそこへ任せるのか。既存の状態と責務が重ならないかまで考えたいです。

だしゅまる：前のスライドから座った姿勢を保ちます。

出典：[Flutter公式のアーキテクチャガイド](https://docs.flutter.dev/app-architecture/guide#ui-layer)、[実際のアーキテクチャ](https://github.com/yakitama5/material_github_searcher/blob/57d9662dcdbfe1a93e6bb0b4706bfa778db8ba05/docs/ARCHITECTURE.md#L132-L137)。画面専用のViewModelを置かずApplication Providerを状態の基準とする点は実装方針に記載されています。MVVMへの賛否や不採用の動機は本人の選定メモにないため断定せず、追加する責務と手間を考える問いとして構成しています。ProviderとViewModelを排他的な技術として比較しません。

## 14 Clean Architectureで、何を守りたい？

06:10–06:50（40秒）

**画面**

> Clean Architectureで、何を守りたい？
>
> 業務ルールを、UIや外部サービスから分ける
>
> 依存の向きを決め、変更の影響を抑える
>
> 境界や変換を保守する手間も引き受ける

実例として「自分の採用例：オニオンアーキテクチャ」を添えます。

**話す**

Clean Architectureでは、業務ルールが外側の実装に依存しないようにします。自分が採用したのは、近い考え方のオニオンアーキテクチャです。AIが速く生成しても、どこを変えてよいか把握しやすくしたかった。

一方、境界やデータ変換を保守する手間は増えます。守りたいものに、その手間が見合うか。そこまで理由にして、他の人にも話せるようになりたいです。

だしゅまる：座位から立ち上がり、「待機」で呼吸や小さな揺れを続けます。

出典：[Clean Architectureの原典](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)、[本人の選定メモ](https://github.com/yakitama5/material_github_searcher/blob/57d9662dcdbfe1a93e6bb0b4706bfa778db8ba05/docs/technical-decisions.md#L36-L51)、[実際の依存関係](https://github.com/yakitama5/material_github_searcher/blob/57d9662dcdbfe1a93e6bb0b4706bfa778db8ba05/docs/ARCHITECTURE.md#L5-L32)。本人が採用した名称はオニオンアーキテクチャです。Clean Architectureと同一とはせず、業務ルールと外部実装を分ける近い考え方として説明します。構造を把握して制御したいという理由は本人の記録、手間との釣り合いは発表用の問いです。
